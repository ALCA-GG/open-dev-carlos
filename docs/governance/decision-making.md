# Toma de decisiones

OpenDev prioriza la transparencia y el aprendizaje. Las decisiones técnicas y educativas deben poder explicarse.

## Principios

1. **Educación primero:** la claridad para quien aprende pesa más que la elegancia para quien ya sabe.
2. **Simplicidad:** se prefiere la solución más simple que cumpla el objetivo.
3. **Consistencia:** se respetan las convenciones existentes salvo que haya una razón documentada para cambiarlas.
4. **Transparencia:** las decisiones importantes se registran en issues, Pull Requests o documentos.
5. **Respeto:** las discrepancias se discuten sobre el código y los argumentos, no sobre las personas.

## Decisiones cotidianas

Las decisiones pequeñas (corregir una errata, mejorar un ejemplo, ajustar un test) se resuelven en el Pull Request correspondiente.

## Decisiones importantes

Se consideran importantes:

- Cambiar la estructura del repositorio.
- Añadir una dependencia o herramienta.
- Modificar la gobernanza o las reglas de contribución.
- Cambiar la versión mínima de Java.
- Alterar el flujo de ramas o de releases.

Para estas decisiones:

1. Abre un issue con contexto, alternativas y consecuencias.
2. Deja un periodo razonable para comentarios.
3. El Owner decide, explicando el motivo.
4. Documenta la decisión en el issue o en un ADR si afecta a la arquitectura.

## Desacuerdos

- Escucha primero.
- Pide ejemplos concretos.
- Distingue entre preferencia y requisito.
- Si no hay consenso, el Owner decide y explica por qué.
- Una decisión puede revisarse si aparecen nuevos datos.

## Cambios en la gobernanza

La gobernanza puede evolucionar hacia un modelo colaborativo de maintainers a medida que la comunidad crezca. Cualquier cambio debe proponerse públicamente y documentarse.

## Registro

Las decisiones relevantes deben quedar enlazadas desde el issue o Pull Request correspondiente. No se toman decisiones importantes solo en conversaciones privadas.
